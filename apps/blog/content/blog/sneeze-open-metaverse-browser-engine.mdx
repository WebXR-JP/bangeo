Metaverse Standards Forum（MSF）は2026年6月15日、Open Metaverse Browser Initiative（OMBI）の一環として、オープンソースのメタバースブラウザエンジン「Sneeze」を発表しました。

まず関係する組織を整理します。Metaverse Standards Forumは、メタバースや空間コンピューティングに関わる標準化団体・企業・開発者をつなぎ、相互運用性の議論を進める業界フォーラムです。RP1は、公式サイトでメタバースブラウザとエコシステムを掲げる企業で、今回のSneezeではリードアーキテクト兼メンテナとして紹介されています。

今回の発表は、MSFの枠組みのもとでRP1が中心となり、空間ブラウザの参照実装をApache 2.0ライセンスのオープンソースとして公開したものです。この記事では、SneezeをSpatial Webや空間ブラウザの隣接トピックとして整理し、WebXR Device APIとの違いを明確にします。

## SneezeとWebXR APIの違い

Sneezeは、ChromeやSafariの中で`navigator.xr.requestSession()`を呼ぶための新しいWeb APIとは性質が異なります。

WebXR Device APIは「WebページからXRデバイス、センサー、HMDにアクセスするためのAPI」です。これに対してSneezeは、「複数の空間サービスを同じ3Dシーンに合成するための、別系統のブラウザエンジン構想」に位置づけられます。WebXRを置き換える存在というより、WebXRの隣で進む空間ブラウザの参照実装として捉えると整理しやすくなります。

## 発表されたSneezeの概要

Sneezeは、MSFとRP1が進めるOMBIから公開された空間ブラウザエンジンで、公式名称は「Open Metaverse Browser Engine」です。OMBIは、空間コンテンツや空間サービスを特定企業の閉じた環境だけに依存させず、標準ベースで扱えるようにするための取り組みです。

公式発表では、Blink、WebKit、Geckoが2Dドキュメント向けのブラウザエンジンであるのに対して、Sneezeは空間コンピューティング向けに設計されたエンジンだと説明されています。既存ブラウザに組み込む構成と、スタンドアロンのネイティブなメタバースブラウザとして動かす構成の双方が想定されています。

主な機能として挙げられているのは、近接ベースの発見機構（proximity-based discovery）、Scene Object Model（SOM）による複数オリジン・複数サービスの3Dシーン合成、サービスごとのWebAssembly（WASM）サンドボックス、そしてAIエージェント・ARグラス・エンタープライズ環境向けのリアルタイムな空間共有（co-presence）です。

1つのWebページがXRセッションを開始するWebXRのモデルと比べ、Sneezeは「現実空間や仮想空間の中で、複数の独立した空間サービスが同時に存在する」ことを前提にしています。

## 中心概念となるSOM（Scene Object Model）

SneezeとOMBIの設計で中心となるのがSOM（Scene Object Model）です。

OMBIのアーキテクチャ文書では、SOMはWebブラウザにおけるDOMに対応する中心インターフェースとして説明されています。DOMが2D文書のツリーを扱うのに対して、SOMは複数の空間サービスが同時に書き込む、階層型・ストリーミング型の3Dシーングラフです。

OMBIでは、従来のWebブラウザとメタバースブラウザの構成要素を次のように対応づけています。

- HTML・CSS・JavaScriptに対して、3D空間コンテンツとWASMサービスロジック
- DOMに対して、SOM
- URLベースのナビゲーションに対して、proximity-based discovery
- JavaScriptエンジンに対して、WASMランタイム
- Blink・Geckoに対して、Sneeze

3D版のHTMLを新たに作る発想というより、空間内の複数サービスを安全に合成するための共有オブジェクトモデルを定義しようとしている点が特徴です。

## 近接ベースで接続する空間サービスモデル

OMBIのアーキテクチャでは、WebのURLナビゲーションに相当する仕組みとして、近接ベースの発見概念（proximity）を採用しています。

WebではURLを入力したりリンクをクリックしたりしてページを開きます。一方、メタバースブラウザでは、ユーザーが倉庫、病院、工場、街角などを移動すると、その場所に関連するspatial fabricやサービスが発見され、近づくと接続され、離れると切断されるモデルを想定しています。

このときのspatial fabricは、WebにおけるWebサイトに近い概念です。都市、大学キャンパス、小売店舗、工場フロア、空港ターミナルなどがspatial fabricとなり、その中に地図サービス、設備情報、商品表示、安全警告、AIエージェント、ユーザーのプレゼンスなどのサービスが紐づきます。

「特定のページからXR体験を開始する」WebXRの発想に対して、SneezeとOMBIは「現実空間を歩くと、その場所に紐づいた複数サービスが同じ3Dシーンに現れる」という発想を採っています。WebARやARグラス時代のUXを考えるうえで参考になる視点です。

## 採用技術：OpenXR・WASM・glTF・ANARI

SneezeのREADMEでは、レンダリングにANARIとHalogen、サンドボックス実行にWebAssembly/Wasmtime、XRデバイスアクセスにOpenXR、シェーダー検証にSPIRV-Tools、ネットワークにcurl、UIにRmlUi、暗号的な信頼検証にBoringSSLとjwt-cpp、構造化データにnlohmann/jsonを使う構成が説明されています。

つまり、WebGLやWebGPUの上にthree.jsを載せるWebXRアプリの構成とは異なり、ネイティブ寄りのエンジン設計です。OpenXRでデバイスへアクセスし、ANARI経由でレンダリングを抽象化し、glTFを3Dアセット形式として扱い、サービスロジックはWASMで隔離して動かします。

WebXR開発者にとっては、今すぐ現場で使うAPIというより、今後の空間ブラウザ設計を読み解くための参照点になります。three.js、Babylon.js、PlayCanvasの学習を置き換えるものではありませんが、glTF、WASM、OpenXR、空間UI、権限モデル、マルチサービス合成を検討する際の比較対象として重要です。

## WebXRとの関係と役割分担

OMBI文書では、Sneezeなどのメタバースブラウザエンジン（MBE）をWebブラウザの置き換えとは位置づけていません。既存Webブラウザに組み込まれる自己完結型のエンジンとして、HTMLレンダラーと共存しながらspatial fabricを扱う可能性も示されています。

両者の違いを整理すると次のとおりです。

### WebXR

- Webページが起点
- ブラウザAPIとして`XRSession`を開始
- WebGL・WebGPU・three.js・Babylon.js・A-Frame・PlayCanvasと相性がよい
- 今すぐ試せる実装環境が整っている

### Sneeze/OMBI

- spatial fabricが起点
- 近接・プレゼンス・複数サービス合成が前提
- OpenXR・ANARI・WASM・glTF・SPIR-Vに加え、spatial fabricと状態を同期する通信プロトコルであるRMAP（Remote Model Access Protocol）を組み合わせる
- 仕様・実装・標準化が進行中の隣接領域

## 現時点での注意点

発表文は大きなビジョンを掲げていますが、現時点では慎重に見ておく必要があります。

SneezeのGitHubリポジトリは公開されていますが、READMEでは静的ライブラリとしてビルドしてアプリケーションに組み込む形が説明されています。今すぐ安定した開発者向けブラウザとして利用できる段階にはなく、初期公開された参照実装・実験実装として捉えるのが安全です。

また、RMAPについても、OMBI文書では今後オープン標準として進める意図が示されている段階です。SOM、RMAP、位置情報抽象化、権限モデル、空間アドレス、開発者ツールなど、これから詰めるべき課題が多く残っています。

## まとめ

Sneezeは、WebXRの対応状況そのものを変える動きというより、Spatial Webの隣接領域として追っておきたい取り組みです。

今すぐWebXRの学習ルートや実装手段が変わるわけではありません。ただし、ARグラス時代に「Webのように空間サービスを開く」仕組みをどう設計するかを考えるうえで、SOM、WASMサンドボックス、OpenXR、RMAPを組み合わせたSneeze/OMBIのアーキテクチャは注目しておく価値があります。
