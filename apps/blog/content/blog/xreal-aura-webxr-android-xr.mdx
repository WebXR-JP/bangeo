## AURAをWebXRの開発対象にする前提

XREAL AURAは、Android XRを搭載する有線XRグラスです。WebXRを使えば、ブラウザから空間に3Dコンテンツを表示し、ハンドトラッキング入力を取り込む体験を開発できます。ただし、Android XRの対応一覧だけを見てAURAで全機能が動くと判断することはできません。本記事は2026年10月13日に確認した公式情報と仕様に基づく技術解説であり、**BANGEOではAURA実機を検証していません**。掲載コードも実機検証済みではありません。

XREALは2026年5月19日のGoogle I/O報告で、旧称Project Aura上のWebXRによる3Dペイントデモを紹介しています。これは公式デモの根拠になりますが、製品版での各セッションモード、OSやChromeのバージョン、必要なフラグまで保証する互換性試験ではありません。[XREALの公式デモ報告](https://www.xreal.com/uk/blog/project-aura-google-io-2026)を出発点に、実際の配信環境で段階的に確かめる必要があります。

## グラスと専用コンピュートパックの構成

[AURAの製品ページ](https://www.xreal.com/us/aura)では、視野角70°の光学シースルー、専用コンピュートパックとの有線構成、6DoFトラッキング（頭の回転に加えて位置の変化も捉える方式）とハンドトラッキングが案内されており、アプリ一覧にもChromeが含まれています。開発時は、グラスだけをPCの外部ディスプレイとして使う経路と、コンピュートパック上のAndroid XR・ChromeでWebXRを開始する経路を区別してください。なお、価格や出荷日は本記事では断定せず、地域ごとの公式案内を確認してください。

従来のXREAL Air・One・Beamシリーズも区別して考える必要があります。[XREAL SDK](https://docs.xreal.com/)のネイティブ機能や3DoFで画面を固定する機能は、ChromeがWebXRセッションを提供する根拠にはなりません。AURAの公式デモをこれらの既存製品へ読み替えず、端末・接続経路・ブラウザごとに判断します。

## Android XRの対応範囲とAURAで未確認の項目

[Android DevelopersのWeb開発ガイド](https://developer.android.com/develop/xr/web)（2026年8月31日更新版）では、ヘッドセットに加えて有線XRグラス（Wired XR Glasses）が対象に含まれています。Android XR版Chromeの対応機能として挙げられているのは、WebXR Device API、AR Module、Gamepads、Hit Test、Hand Input、Anchors、Depth Sensing、Light Estimationです。ただし、これはあくまでプラットフォーム全体の案内であり、AURA製品版での個別実測とは分けて扱う必要があります。

| 確認する対象 | 現時点の根拠と次の確認 |
| --- | --- |
| AURAでのWebXR体験 | 公式3Dペイントデモあり。製品版の実機検証待ち |
| `immersive-ar`・`immersive-vr` | 両モードの個別実測は未確認。ブラウザでそれぞれ診断 |
| ハンドトラッキング・コントローラー | プラットフォーム対応と製品ページでのハンドトラッキング案内あり。入力プロファイルや実データは未確認 |
| 深度センシング・アンカー | Android XRの一覧に記載。AURAの許可条件・取得条件は未確認 |
| Layers・WebGPUのXR連携 | AURAでの対応は未確認。通常のWebGPU対応から推定しない |

## HTTPS上でのセッション診断

まずHTTPSでページを配信し、AURA上のChromeで開きます。`localhost`に対する開発用例外は端末自身でのアクセスに限られるため、PCのHTTP URLへ接続するだけでは同じ条件になりません。iframe内に埋め込む場合は、埋め込み元のPermissions Policyで`xr-spatial-tracking`が許可されているかも確認します。

次のHTMLは、**描画を行わずARセッションの開始と終了だけを診断する例**です。両モードに対応しているかの確認（`isSessionSupported`）はページ読み込み時に実行し、セッションの開始要求はボタンクリックから直接呼び出します。`isSessionSupported`が`true`を返しても、権限拒否や端末の状態によっては開始に失敗することがあります。

```html
<button id="start" disabled>ARセッションを診断</button>
<pre id="log"></pre>
<script type="module">
  const button = document.querySelector('#start');
  const output = document.querySelector('#log');
  const log = (value) => { output.textContent += `${value}\n`; };
  const xr = navigator.xr;
  log(`secure context: ${window.isSecureContext}`);

  if (!window.isSecureContext || !xr) {
    log('HTTPSとnavigator.xrを確認してください');
  } else {
    for (const mode of ['immersive-ar', 'immersive-vr']) {
      try {
        log(`${mode}: ${await xr.isSessionSupported(mode)}`);
      } catch (error) {
        log(`${mode}: ${error.name}: ${error.message}`);
      }
    }
    button.disabled = false;
  }

  button.addEventListener('click', async () => {
    button.disabled = true;
    let session;
    let ended = false;
    try {
      session = await xr.requestSession('immersive-ar', {
        optionalFeatures: ['hand-tracking'],
      });
      session.addEventListener('end', () => { ended = true; });
      log(`blend mode: ${session.environmentBlendMode}`);
      log(`enabled features: ${session.enabledFeatures
        ? Array.from(session.enabledFeatures).join(', ')
        : 'このブラウザでは参照不可'}`);
      log('開始成功。描画・手の実データは検証していません');
    } catch (error) {
      log(`${error.name}: ${error.message}`);
    } finally {
      if (session && !ended) {
        try {
          await session.end();
        } catch (error) {
          log(`終了処理: ${error.name}: ${error.message}`);
        }
      }
      button.disabled = !window.isSecureContext || !xr;
    }
  });
</script>
```

`optionalFeatures`は未対応でもセッション開始を妨げない指定のため、開始に成功しただけで`hand-tracking`が有効になったとは限りません。`enabledFeatures`を参照できる場合は許可された機能を確認し、描画を含むサンプルで実際に手のデータが届くかも確かめます。参照できない場合は「未確認」として記録し、有効化されていると推定しないでください。セッション開始とユーザー操作の要件は[WebXR Device API仕様](https://immersive-web.github.io/webxr/)を参照できます。

## 描画と入力を切り分ける実機確認

セッション診断の後は、[公式WebXR Samples](https://immersive-web.github.io/webxr-samples/)を使って動作を確認します。AndroidのガイドにはARの開始例とVRのハンドトラッキングサンプルが用意されているため、ARとVRをそれぞれ個別に試してください。頭の回転や移動に合わせて空間上の物体の見え方が変わるか、左右両眼に正しく描画されるか、終了後に通常のページ操作へ戻れるかを確認します。単眼のスマートフォンARから移植する場合は、両眼それぞれの`XRView`に対応した描画処理が必要です。

ハンドトラッキングでは、各`XRInputSource`の`hand`、`handedness`、`profiles`を記録します。手が検出されていても、手が隠れたりトラッキング範囲外に出たりすると関節の姿勢情報（pose）が取得できなくなるため、`getJointPose()`が`null`を返すフレームを安全に処理してください。左右の手やコントローラーの識別は配列順に頼らず、入力ソースの追加・削除にも対応させます。[Hand Input仕様](https://immersive-web.github.io/webxr-hand-input/)に沿って、トラッキングを失った手で操作が継続しない設計にします。

深度センシングでは、単眼の深度画像を両眼へ流用せず、`pose.views`の各ビューに対応する深度データを扱います。ビューアーの姿勢情報や深度データが得られないフレームはスキップし、取得方式・解像度・更新頻度も記録しておきます。また、アンカーの生成・追跡と、セッションをまたぐ永続化は別の機能です。アンカーを作成できただけで、再起動後も同じ位置へ復元できるとは判断できません。

## 光学シースルーでの見え方と確認記録

光学シースルー方式では現実世界を直接見るため、カメラ映像を背景に合成するパススルー方式とは見え方が異なります。`session.environmentBlendMode`の値を実際に読み取り、加算合成など返された方式に合わせて背景色や配色を設計してください。黒背景で現実を完全に覆い隠せるとは仮定せず、明るい環境での文字の可読性、薄い色の視認性、視野の端での表示切れを実機で確かめます。製品の調光機能がWebXR側から制御できるとも断定できません。

検証時の記録には、次の項目を残しておくと原因の特定に役立ちます。

- 端末名、OSおよびChromeのバージョン、検証URL
- セッションモード、フラグの状態、要求機能・許可機能
- 入力プロファイル、実データの有無、発生したエラー

なお、通常のWebページでWebGPUが使えても、WebXRの描画でそのまま使えるとは限りません。LayersやWebGPU連携は別項目として、使用するフレームワークとブラウザの組み合わせごとに検証します。

## まとめ

XREAL AURAにはWebXRの公式デモがあり、Android XR版Chromeにはハンドトラッキングや空間情報を扱うAPIの対応案内が出ています。実機検証は、HTTPS環境でのAPI確認、モード別の対応確認、ユーザー操作によるセッション開始、描画と実データ取得の順に進めると原因を特定しやすくなります。プラットフォーム全体の案内とAURA製品版での実測を分けて扱い、姿勢情報が取得できないケースや権限拒否の挙動まで含めて記録しておくことが、安定したWebXR開発につながります。
