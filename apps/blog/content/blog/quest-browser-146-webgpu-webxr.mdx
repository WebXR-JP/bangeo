Meta Horizon OS Developersのリリースノートで、**Quest Browser 146.0にWebXR向けの実験的なWebGPU対応とWebXR Depth Projection（深度投影）対応が追加された**ことが発表されました。あわせて、レンズキャリブレーションやWebXRの`bounded-floor`空間に関する不具合の修正、Quest Browser 146.1でのQuest 3以降向けブラウザウィンドウ壁固定機能の更新も案内されています。

## 146.xの更新サマリー

| バージョン | 日付 | WebXR/WebGPU関連の見どころ | 現時点での位置づけ |
| --- | --- | --- | --- |
| Quest Browser 146.0 | 2026年4月21日 | WebXR向けの実験的なWebGPU対応、WebXR Depth Projection対応、レンズキャリブレーション修正、`bounded-floor`空間の不具合修正、Chromium 146ベースへの更新 | WebGPU・Depth Projectionともに実験段階（要フラグ・実機検証） |

今回のポイントは、Quest Browser上のWebXRでWebGLに加えてWebGPUを使う道が開き始めたことと、MR向けの深度投影（WebXR Depth Projection）がブラウザ側の実験対象に入ったことです。WebXR Depth ProjectionはQuest Browser 146で実装されたWebXR Depth Sensing関連の機能で、深度テクスチャを用いて現実空間と仮想オブジェクトのオクルージョン（遮蔽表現）を実現します。現時点では実験機能のため、通常のWebXRコンテンツが自動的にWebGPUへ切り替わるわけではありません。Quest Browserで`chrome://flags`を開き、`webXR experimental features`を有効にするとAPIが利用可能になります。

## WebXRでWebGPUが使える意味

WebXRは、ブラウザからVRやARのセッションを開始し、ヘッドセットの姿勢、コントローラー、ハンドトラッキング、空間マッピング（Questではシーンキャプチャとして提供）などを扱うためのWeb APIです。これまでWebXRの描画はWebGLを前提にした実装が中心でした。

一方でWebGPUは、Vulkan、Metal、Direct3D 12のような現代的なGPU APIに近い設計のWeb標準です。低レベルなGPU制御、計算処理、複雑なレンダリングパイプラインを扱いやすくするためのAPIで、WebXRと組み合わせることで次のような領域での恩恵が期待できます。

- GPU負荷の高いXRレンダリング
- 大量のオブジェクトやパーティクルを扱うシーン
- コンピュートシェーダーを使ったシミュレーション
- WebGPU前提で作られた3DエンジンやレンダラーのWebXR対応

ただし、今回の機能はまだ実験段階です。本番環境で前提にするのではなく、開発者が早い段階で試し、挙動や制約を確認してフィードバックするための段階と捉えるのが現実的です。

## WebXR Depth Projectionとbounded-floor修正

146.0では、ブラウザ内のWebXR Depth Projectionサポートも追加されました。QuestのMR環境で現実空間の奥行きと仮想オブジェクトのオクルージョンを検証するうえで重要な更新です。ただし、深度投影は端末、権限、セッションモード、実験フラグ、ブラウザ実装の組み合わせに強く依存するため、本番採用ではなく実験的な検証テーマとして追う必要があります。

同じリリースでWebXRの`bounded-floor`空間に関する不具合が修正された点も、ルームスケール系デモ（`bounded-floor`/`local-floor`）では重要です。これらを使うデモでは、`boundsGeometry`の取得、床の高さ、再センタリング後の座標、左右の目での表示に破綻がないかをQuest Browser 146.x以降で再確認しておくと安心です。

## 有効化方法

Quest Browser 146.0で試す場合は、次の手順になります。

1. Quest Browserで`chrome://flags`を開く
2. `webXR experimental features`を検索する
3. フラグを有効化する
4. ブラウザを再起動する
5. WebGPU in WebXRに対応したサンプルや実装を開く

WebGPUそのものの対応状況や、WebXRとのバインディングの有無はブラウザやバージョンによって変わります。開発時は`navigator.gpu`、`navigator.xr`、`XRGPUBinding`などの存在を確認しながら、未対応環境向けのフォールバックを用意しておくのが現実的です。

```javascript
const supportsWebGpu = "gpu" in navigator;
const supportsWebXr = "xr" in navigator;
const supportsXrGpuBinding = "XRGPUBinding" in window;

console.log({
  supportsWebGpu,
  supportsWebXr,
  supportsXrGpuBinding,
});
```

## HTMLをテクスチャとして描画する動き

この投稿へのリプライでは、Richard Anaya氏から「HTMLをテクスチャとして描画する実験的な取り組みもサポートされる予定か」という質問が寄せられました。これに対し、Cabanier氏は次のように回答しています。

> **Rik Cabanier氏:** GoogleがHTML-in-Canvasに取り組んでおり、ChromeとQuest Browserで実験的に動作しています。HTMLを直接テクスチャへ描画できるようになります。WebXRでのヒットテストには追加サポートが必要ですが、後で対応する予定です。

[WICGのHTML-in-Canvas提案](https://github.com/WICG/html-in-canvas)では、Canvas内でHTMLコンテンツを描画するためのAPIが説明されています。Chromiumでは`chrome://flags/#canvas-draw-element`から有効化できる実験的APIとして紹介されており、WebGL/WebGPU向けにはHTML要素をテクスチャへコピーする方向も含まれています。

XR空間内のUIはこれまで3DメッシュやCanvasで独自実装することが多く、通常のHTML/CSS UIをそのまま3D空間のパネルに貼ることは簡単ではありませんでした。HTML-in-Canvasが進めば、HTMLで作った設定パネル、メニュー、カード、フォームなどをWebGPUやWebGLのテクスチャとしてXR空間へ配置しやすくなります。

## 現時点での注意点と今後の見通し

今回のアップデートには、次のような制約が残っています。

- Quest Browser 146.0時点では実験機能として提供されている
- `chrome://flags`での有効化が必要
- API仕様や実装挙動は今後変わる可能性がある
- WebXR内でのHTML UIのヒットテストなど、周辺機能には未対応部分が残る

Quest BrowserでWebGPUとWebXRの連携が動き始めたことで、WebGL中心だったWebXRの描画基盤を現代的なGPUパイプラインへ広げる道筋が見えてきました。さらにHTML-in-Canvasのような取り組みが加われば、HTML/CSSのUI表現とXR空間での描画も近づいていきます。

もっとも、一般ユーザー向け機能の必須要件とするにはまだ早い段階です。まずは検証環境でAPIの挙動やフォールバック動作を確認し、将来のレンダリング基盤に備える材料として試してみるのがよいでしょう。
