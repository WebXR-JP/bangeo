WebXRの標準仕様まわりで、開発者が押さえておきたい更新が入っています。

今回注目したいのは、[WebXR Device API](https://www.w3.org/TR/webxr/)の`inline-stereo`と、[WebXR Layers API Level 1](https://www.w3.org/TR/webxrlayers-1/)の`space-warp`です。WebXR Device APIは2026年6月9日付けの[勧告候補草案（CRD）](https://www.w3.org/TR/webxr/)として、WebXR Layers API Level 1は2026年6月1日付けの[ワーキングドラフト（WD）](https://www.w3.org/TR/webxrlayers-1/)として公開されています。

どちらも今すぐ全ブラウザで広く使える機能という位置づけではありませんが、今後の互換性設計や実機検証の項目を見直すうえで重要な仕様更新です。BANGEOの[標準化・対応状況ページ](/webxr-status)でも、これらの仕様を継続的に追跡しています。

## inlineセッションの役割とセッションモードの違い

WebXR Device APIで定義されている主要なセッションモード（`XRSessionMode`）は、`inline`、`immersive-vr`、`immersive-ar`の3種類です。

```javascript
await navigator.xr.requestSession("inline");
await navigator.xr.requestSession("immersive-vr");
await navigator.xr.requestSession("immersive-ar");
```

| モード | 役割 | 主な用途 |
| --- | --- | --- |
| `inline` | Webページ内でXRアプリを非没入状態で動かす | 3Dプレビュー、VR/ARへ進む前の入口表示 |
| `immersive-vr` | 仮想空間へ没入する | VR空間、研修、ゲーム、3D展示 |
| `immersive-ar` | 現実空間にXR表示を重ねる | 家具配置、ARガイド、MRデモ |

通常の画面で見る限り、`inline`セッションは一般的な3D canvasとよく似ています。実際、描画先としてWebページ内のcanvasを使う点も同じです。

違いは見た目ではなく役割にあります。通常のcanvasが「ページ内に3Dモデルを表示するための領域」であるのに対し、`inline`セッションはWebページの中でXR体験をプレビューし、対応端末ならそのまま`immersive-vr`や`immersive-ar`へ移行するための入口として機能します。たとえば家具の商品ページなら、ページ内で椅子の3Dモデルを確認し、続けてVRでの実物大表示やARでの部屋配置へつなぐ流れの出発点になります。

## WebXRと3Dエンジンの役割分担

ここで整理しておきたいのが、WebXR自体は3D描画エンジンではないという点です。WebXRはXRデバイスとブラウザをつなぎ、ビュー、描画タイミング、入力、デバイス状態を管理するAPIです。実際の3D描画はthree.js、Babylon.js、A-Frame、PlayCanvasなどのライブラリや、WebGL/WebGPUによる実装が担います。

- **WebXR**：XRデバイスとブラウザをつなぐAPI
- **three.jsなど**：3Dシーンを描画するライブラリ
- **canvas**：Webページ内で描画領域を提供する要素
- **セッション**：どの表示形態（`inline`・`immersive-vr`・`immersive-ar`）でXRを開始するかの単位

## inline-stereoの仕組み

`inline-stereo`は、新しいセッションモードではなく、`inline`セッションで左右2つの視点を扱えるようにする機能記述子（feature descriptor）です。

通常の`inline`セッションでは描画に使うビューが1つ（`view.eye`は`"none"`）ですが、`inline-stereo`が有効な対応環境では、ビュー一覧に`"left"`と`"right"`の2つのプライマリビューが含まれます。

これにより、ヘッドセット内のブラウザや空間ディスプレイ上で、Webページに埋め込まれた3Dコンテンツを立体的に表示できるようになります。たとえば記事中の3D地球儀が奥行きのある球体に見えたり、商品ページの3Dスニーカーや建築モデルがページ内の小さな模型のように浮き上がって見えたりする表現が想定されます。

`immersive-vr`が仮想空間へ没入するためのモードであるのに対し、`inline-stereo`はあくまでWebページ内の3D表示を立体化する仕組みです。仕様上、`inline-stereo`は`"inline"`セッションにのみ適用され、没入型セッションには付与されません。そのため、本格的なVR体験を作る場合はこれまでどおり`immersive-vr`を使います。

## PR #1436の議論から見えるinline-stereoの設計ポイント

`inline-stereo`は最初から現行の形だったわけではありません。Immersive Webの[PR #1436](https://github.com/immersive-web/webxr/pull/1436)では、当初`inline-stereo`を新しいセッションモードとして追加する案から議論が始まりました。ユーザー操作で要求された場合に空間権限を求める挙動や、ヘッドトラッキングが許可されない場合に固定ステレオ表示へ切り替える案も検討されていました。

最終的な[WebXR Device API仕様](https://www.w3.org/TR/webxr/)では、`inline-stereo`を`XRSessionMode`には加えず、`inline`セッション向けの機能記述子として位置づけています。したがって、`requestSession("inline-stereo")`ではなく、`"inline"`セッションの`optionalFeatures`または`requiredFeatures`で指定します。

レビューの過程では、一時的に`head-tracked`という機能記述子を追加する案も出ましたが、「ヘッドトラッキングを得るために毎回`head-tracked`を要求しなければならない」と誤解される懸念が指摘されました。その結果、記述子自体は削除され、トラッキングが必要な場合は既存のリファレンススペース（特に`local`）の仕組みに寄せる方針で整理されています。

実装するうえで押さえておきたいのは、`inline-stereo`は**ステレオ表示を要求する機能であり、ヘッドトラッキングを有効化する機能ではない**という点です。空間トラッキングが必要な場合は、リファレンススペースの要求と権限の扱いを別途検討する必要があります。仕様本文でも、`inline`セッションでの`local`リファレンススペース利用にはユーザー同意が必要と整理されています。

射影行列（projection matrix）とビュー行列（view matrix）の計算方法も論点になりました。トラッキング付きのステレオ`inline`表示において、canvasを「ページの奥にある等身大の3D世界への窓」として扱うのか、HTMLの`<model>`要素のようにページ上の面に結びついたジオラマ的な空間として扱うのかが議論されています。現行仕様では、`inline-stereo`が有効な場合、ユーザーエージェントが出力canvasのジオメトリを使ってビューごとの射影行列を計算すると説明されています。ただし、PR自体は2026年6月9日にマージされたものの（[マージコミット](https://github.com/immersive-web/webxr/commit/f19a6dd3a0136a2a16fbaf368cfd8563a6af0dcb)）、実装間の解釈差が出やすい領域として追加詳細化の余地が残されています。

アクセシビリティ面の議論もありました。ユーザーエージェントが`inline-stereo`対応を返しながら、アクセシビリティ上の配慮で片方のビューのみを表示したり左右に同じ行列を返したりすることを認めるかという論点です。最終的には許容しない方向で整理され、必要に応じて開発者側が`inline-stereo`を`optionalFeatures`で要求する形が示されています。

現時点での要点をまとめると、次のとおりです。

- `inline-stereo`は新しいセッションモードではなく、`inline`セッション向けの機能記述子
- ヘッドトラッキング自体を有効化する機能ではなく、トラッキング要件はリファレンススペースと権限で別途確認する
- 対応環境では`pose.views`に`"left"`と`"right"`の2つのビューが入る
- 射影行列・ビュー行列の細かい解釈は、今後のブラウザ実装差分に注意する

## inline-stereoを見据えた実装上の注意点

`inline-stereo`を必須（`requiredFeatures`）にすると、非対応環境でセッション開始に失敗する可能性があります。まずは`optionalFeatures`で要求し、`enabledFeatures`で有効化を確認する設計が現実的です。これにより、対応環境ではステレオ表示、非対応環境では従来の単眼`inline`表示へ自然にフォールバックできます。

```javascript
const session = await navigator.xr.requestSession("inline", {
  optionalFeatures: ["inline-stereo"],
});

const supportsInlineStereo =
  session.enabledFeatures?.includes("inline-stereo") ?? false;
```

描画ループでも、`inline`セッションだからといって`pose.views[0]`だけを参照する書き方は避けるのが安全です。次のように`pose.views`をループして各ビューのビューポートを取得・描画しておけば、通常の単眼`inline`（`"none"`）と`inline-stereo`（`"left"`・`"right"`）の両方に対応できます。

```javascript
const referenceSpace = await session.requestReferenceSpace("viewer");

session.requestAnimationFrame((time, frame) => {
  const pose = frame.getViewerPose(referenceSpace);
  if (!pose) return;

  for (const view of pose.views) {
    const viewport = glLayer.getViewport(view);

    gl.viewport(
      viewport.x,
      viewport.y,
      viewport.width,
      viewport.height
    );

    // 通常のinlineでは view.eye は "none"
    // inline-stereo対応環境では "left" / "right" になる可能性がある
  }
});
```

## WebXR Layers APIにおけるSpace Warpの更新

もうひとつ注目したいのが、WebXR Layers API Level 1（2026年6月1日付けワーキングドラフト）に含まれる`space-warp`の記述更新です。WebXR Layers API Level 1は、WebXRセッション内で複数のレイヤー種別を扱うための仕様です。

仕様内では、Space WarpはXRコンポジターの再投影（reprojection）を改善する技術として説明されています。アプリが動きベクトルを格納した`motionVectorTexture`と深度情報を含む`depthStencilTexture`を提出することで、XRコンポジターが前フレームから現在フレームを補間・外挿し、低いフレームレートで動作させながらも滑らかな表示を保つ仕組みです。

[Meta for Developers](https://developers.meta.com/horizon/documentation/web/webxr-space-warp/)のドキュメントでも、WebXR Space WarpはWebXR Layers仕様へのドラフト追加として紹介されており、アプリが渡すモーションベクターと深度データを使ってXRコンポジターが再投影・フレーム補間を行う構成が解説されています。Quest Browserで[WebGPU in WebXRを試す](/tech-articles/quest-browser-146-webgpu-webxr)際にも、Layers関連の実験機能とあわせて検証対象になりやすい領域です。

## モーションベクターと深度データの提出条件

Space Warpを使う場合、アプリ側は通常のカラー描画に加えて`motionVectorTexture`とシーンの深度データを用意する必要があります。

仕様では、`space-warp`を有効にした場合、XRコンポジターは深度値を使用する必要があり、`ignoreDepthValues`は`false`、`usesDepthValues`は`true`になるとされています。さらに、`motionVectorTexture`または`depthStencilTexture`のいずれかが提出されなかったフレームは、Space Warpが無効として扱われることが明記されています。

つまり、セッション開始時に機能を有効化しただけでは十分ではなく、フレームごとに必要なテクスチャを欠かさず提出できているかが重要になります。

```javascript
const session = await navigator.xr.requestSession("immersive-vr", {
  requiredFeatures: ["layers"],
  optionalFeatures: ["space-warp"],
});
```

実機で検証する際は、カラーテクスチャだけでなくモーションベクターテクスチャと深度ステンシルテクスチャが毎フレーム正しく更新されているか、半透明オブジェクトや高速に移動するオブジェクトで描画が破綻しないかを確認する必要があります。

## 実験機能としてのSpace Warpの現在地

Space Warpは高負荷シーンの最適化に有望な手段ですが、現時点では本番前提の標準機能ではなく検証段階の技術として扱うのが安全です。

Metaのドキュメントでも、WebXR Space Warpは実験機能とされており、Quest Browserでは`chrome://flags`から有効化する必要があると案内されています。また、利用条件として`EXT_color_buffer_half_float`、`layers`、`space-warp`、`texture-array`などが挙げられています。高負荷なWebXR表現を見据えて、今のうちに仕組みと制約を検証しておく位置づけが適切です。

## 既存のWebXR実装で見直したい2つのポイント

今回の仕様更新を受けて、既存のWebXRコンテンツで見直しておきたい点は大きく2つあります。

1つ目は、`inline`セッションのビュー数を1つと決め打ちしないことです。`inline-stereo`対応環境を想定し、`pose.views`のループ処理と`optionalFeatures`によるフォールバックを前提にしておくと将来の互換性を保ちやすくなります。

2つ目は、Space Warpを検証する際にモーションベクターと深度データの提出条件を確認することです。機能が有効になっているかだけでなく、各フレームで必要なテクスチャが正しく渡されているかまで実機でチェックする必要があります。

WebXRは基本的なVR/AR表示から、レンダリングパスやレイヤー構成、機能記述子を細かく制御する段階へと進んでいます。仕様の更新を追いながら、ビュー数の前提やフォールバック設計、実機での検証項目を継続的に見直していくことが大切です。
