XRでは、通常のWebページや2Dゲームよりも描画負荷が高くなりがちです。

VRやARでは左右の目に別々の映像を出力する必要があり、さらに高いフレームレートも求められます。ヘッドセットの表示解像度が上がるほどGPUが処理するピクセル数は増え、影、ポストエフェクト、PBR、パーティクル、Gaussian Splatting、動画テクスチャなどのリッチな表現を加えるほど負荷は大きくなります。

こうした高負荷への対策として注目されているのが、**フォービエイテッドレンダリング（foveated rendering）**です。

人間の視覚は中心視野では細部まで鮮明に捉えられる一方、周辺視野では細かい情報を識別しにくい性質があります。フォービエイテッドレンダリングはこれを利用し、画面の中心や注視点の周囲は高品質に描き、周辺部の解像度やシェーディングレート（Variable Rate Shading）を下げることで、見た目の劣化を抑えながらGPU負荷を軽減します。

## WebXRで利用できる固定フォービエーション

[WebXR Layers API Level 1](https://www.w3.org/TR/webxrlayers-1/)には、`XRProjectionLayer.fixedFoveation`という属性が定義されています。W3Cの仕様では、XRコンポジターが適用するフォービエーション強度を0（最小）から1（最大）の範囲で指定でき、非対応のブラウザやデバイスでは`null`を返して設定を無視（no-op）するとされています。値の変更は次の`XRFrame`から反映されます。

```javascript
const glBinding = new XRWebGLBinding(session, gl);
const projectionLayer = glBinding.createProjectionLayer();

if (projectionLayer.fixedFoveation !== null) {
  projectionLayer.fixedFoveation = 0.5;
}
```

[MDN](https://developer.mozilla.org/en-US/docs/Web/API/XRProjectionLayer/fixedFoveation)でも、`fixedFoveation`はXRコンポジターがレイヤーに適用する強度を表す数値であり、固定フォービエイテッドレンダリング（Fixed Foveated Rendering、FFR）によって各眼のテクスチャ周辺部を中心より低解像度で描き、GPU負荷を抑える仕組みとして説明されています。

[Meta for Developers](https://developers.meta.com/horizon/documentation/web/webxr-ffr/)のドキュメントによると、FFRは各眼向け描画バッファ（アイバッファ）の周辺部を低解像度で描画してレンダリングコストを節約する技術で、フラグメントシェーダーの処理がボトルネックになりやすいアプリで特に効果を発揮します。Quest Browserでは、セッション開始時のオプショナル機能（`optionalFeatures`）や実行時の`fixedFoveation`属性で強度を調整する方法が案内されています。

```javascript
const sessionInit = {
  requiredFeatures: ["local-floor"],
  optionalFeatures: ["high-fixed-foveation-level"],
};

const session = await navigator.xr.requestSession("immersive-vr", sessionInit);
```

## 固定フォービエーションの向き不向き

固定フォービエーション（fixed foveation）は、視線追跡（eye tracking）を使わず、あらかじめ固定されたパターンで画面周辺の品質を下げる方式です。中心付近を高品質に保ちつつ周辺を落とすため、背景やコントラストの低いシーンでは劣化が目立ちにくい傾向があります。

一方で、UI、細かい文字、コントラストの高い線、ミニマップ、遠方にある小さなオブジェクトなどでは画質の低下が分かりやすくなります。Metaのドキュメントでも、高コントラストな表現やテキストが多いシーンでは描画の乱れ（アーティファクト）が目立つ場合があるため、視覚品質への影響を評価するよう注意喚起しています。

したがって、固定フォービエーションは「とりあえず強度を上げればよい設定」ではありません。GPU負荷、画質、UIの読みやすさのバランスを実機で確認しながら調整する必要があります。

## 中間バッファやポストエフェクト構成での注意点

WebXRアプリでは、一度自前のレンダーターゲットにシーンを描画し、ポストエフェクトをかけてから最終フレームへ出力する構成がよく使われます。

しかしMetaのドキュメントでは、FFRが効かなくなる主な原因として、シーンを中間バッファに描いてから最終フレームへポスト処理する構成や、1フレーム内でレンダーターゲットを切り替える構成が挙げられています。FFRは最終的なアイバッファへの描画に作用するため、レンダリングパイプラインの組み方によっては期待どおりの効果が得られません。

この点は[three.js r184のWebXR更新](/tech-articles/threejs-r184-webxr-layers-hand-model-cache)を利用する場合にも関わります。レンダラーやポストプロセスの構成次第で、ブラウザやデバイス側のフォービエーションがどこまで機能するかが変わる可能性があります。

## 動的フォービエーションの可能性と視線データの課題

さらに高い最適化効果が期待できるのが、ユーザーが実際に見ている位置に合わせて品質を変える動的フォービエーション（dynamic foveation）です。視線追跡対応デバイスでは、注視点の周辺だけを高品質にし、それ以外の領域を大きく落とせるため、固定式以上の負荷軽減が見込めます。なお、視線追跡の標準化自体はWebXRやOpenXRで拡張仕様として議論が続いています。

ただしWeb環境では、視線データの扱いが大きなハードルになります。ユーザーがどこを見ているかという情報は、関心、認知状態、健康状態、意図の推測につながり得る極めてセンシティブなデータだからです。

[Immersive WebのGitHub Issue](https://github.com/immersive-web/webxr/issues/1420)では、動的フォービエーションをWebXRへ導入する場合、Webコンテンツ側へ視線データを露出しない設計が必要であると提起されています。

2026年5月の[Immersive Web対面会議](https://www.w3.org/2026/05/19-immersive-web-minutes.html)でも、フォービエーションのWebXR API化が議論されました。議事録では、WebGPUやVariable Rate Shadingとの関係、フォービエーションマップの扱い、視線追跡由来の情報が漏洩するプライバシーリスク、読み戻し（readback）を防げるかといった点が論点になっています。

動的フォービエーションの実現には、描画性能だけでなくWebXR、WebGPU、ブラウザのセキュリティモデル、プライバシー保護まで一体で設計する必要があります。現時点では仕様議論が進んでいる段階のテーマとして捉えるのが妥当です。

## WebGPUとの関わり

フォービエーションをより一般化すると、Variable Rate ShadingやVariable Rasterization RateといったGPU機能に近い領域になります。WebGPU側でも[Variable Rasterization Rateに関するIssue](https://github.com/gpuweb/gpuweb/issues/450)で、フラグメントシェーダーの実行密度を領域ごとに変えて性能と画質のバランスを取る仕組みが議論されています。ただし、Vulkan、D3D12、Metalで仕様が異なるため、相互運用できるAPI設計の難しさも指摘されています。

Immersive Webの議事録でも、WebXR側だけで完結せずWebGPUワーキンググループとの連携が必要になる点が挙げられています。

今後の高品質なWebXR開発では、WebGLだけでなくWebGPUとの接続がますます重要になります。[Quest Browser 146.0でWebGPU in WebXRが実験的に利用可能に](/tech-articles/quest-browser-146-webgpu-webxr)なった流れとあわせて、高解像度ヘッドセットや空間コンピューティング端末では、フォービエーション、Layers、WebGPU、コンポジターそれぞれの役割分担が性能を大きく左右します。

## 現時点で取り組める実践的な対策

いまWebXR開発者が実践できるのは、基本的なパフォーマンス計測と設計を丁寧に進めることです。

1. **ターゲットデバイスでフレームタイムを計測する**：平均FPSだけでなく、GPUとCPUのどちらがボトルネックか、解像度を下げたときに改善するかを確認します。
2. **固定フォービエーションを低い値から試す**：対応環境では少しずつ強度を上げ、UIや文字が読みにくくなる場合は強度を下げる、UIを視野中心寄りに配置する、文字を大きくする、重要な情報を別レイヤーへ分けるといった対策を検討します。
3. **ポストエフェクト構成とFFRの相性を確認する**：中間バッファにすべて描いてから合成するパイプラインでは、デバイス側のフォービエーション効果が薄れる場合があるため、実機で効き方を確かめます。
4. **動的フォービエーションやWebGPU連携は仕様動向を追う**：今すぐ本番導入する手法ではなく、今後の標準化トピックとして継続的にチェックしておきます。
