WebXRでUIを作るとき、多くの開発者が最初に悩むのは「ボタン、テキスト、フォーム、メニューをどう実装するか」という点です。

three.jsやBabylon.js、PlayCanvasなどで3D空間を構築する場合、UIもメッシュ、テクスチャ、レイキャスティング、独自イベント処理で実装できます。VR空間内のボタン、3Dメニュー、手やコントローラーで操作するパネルなどは、現在もこの方法で作られることが多くあります。

ただし、HTML/CSSがもともと得意とする機能をWebGL側で再実装するのは容易ではありません。複数行テキスト、フォーム入力、アクセシビリティ、翻訳、コピー＆ペースト、右クリック、フォーカス管理、スクリーンリーダー対応などを、3Dエンジン側だけで自然に扱うのは大きな負担になります。

そのため最近のImmersive Web周辺では、WebXRのUIをすべて3Dで作り直すのではなく、**HTML/CSSの強みをXR空間へどう持ち込むか**という議論が広がっています。代表的なアプローチが、DOM Overlay、HTML-in-Canvas、Spatial CSSの3つです。

## 実用段階にあるDOM Overlay

[WebXR DOM Overlays Module](https://www.w3.org/TR/webxr-dom-overlays-1/)は、没入型WebXRセッション中にインタラクティブな2D DOMコンテンツを表示する仕組みです。W3Cの仕様では、有効化するとユーザーエージェントが単一のDOM要素の内容を透明背景の2D矩形として表示すると説明されています。なお、この仕様はワーキングドラフト段階であり、APIは今後も変更される可能性があると明記されています。

DOM Overlayが適しているのは、AR画面の上に説明テキストやメニュー、設定パネル、購入ボタンなどを重ねたいケースです。通常のHTML/CSSでUIを記述できるため、Web開発者にとって導入しやすい点が大きな利点です。

セッション開始時に`dom-overlay`をオプショナル機能（`optionalFeatures`）として要求し、オーバーレイのルートとなるDOM要素を指定します。UI側では通常どおりCSSでボタンやパネルをスタイリングできます。

```javascript
const session = await navigator.xr.requestSession("immersive-ar", {
  optionalFeatures: ["dom-overlay"],
  domOverlay: { root: document.getElementById("xr-ui") },
});
```

DOM Overlayでは、ユーザーがDOM UIを操作した際にWebXR側の`select`イベントと重複しないよう、`beforexrselect`イベントでXR入力を抑制できます。仕様では、DOM Overlay上の特定領域で`preventDefault()`を呼ぶことで、対応するWebXRの`selectstart`・`selectend`・`select`イベントを抑えられる仕組みになっています。

```javascript
document
  .getElementById("menu")
  .addEventListener("beforexrselect", (event) => {
    event.preventDefault();
  });
```

ただしDOM Overlayは、基本的には「WebXR映像の上に2D UIを重ねる」仕組みです。3D空間内の任意の位置にHTMLパネルを配置する、球面にHTMLを貼る、3Dオブジェクトの一部としてDOMを自然に組み込むといった用途にはそのままでは向きません。

[BANGEOの標準化・対応状況](/webxr-status)でも、DOM Overlays Moduleはワーキングドラフト段階の機能として追跡しています。

## DOMをテクスチャとして3D空間に置くHTML-in-Canvas

次に注目されているのがHTML-in-Canvasです。これは、HTMLコンテンツを2D canvasやWebGL/WebGPUの描画先に取り込むための提案です。[WICGの解説文書（explainer）](https://github.com/WICG/html-in-canvas)では、`layoutsubtree`属性、DOM要素をcanvasへ描画するメソッド、更新を扱う`paint`イベントという3つの主要プリミティブが説明されています。

[Chrome for Developersの記事](https://developer.chrome.com/blog/html-in-canvas-origin-trial)によると、HTML-in-Canvas APIはChrome 148〜150のオリジントライアルで提供され、Chrome Canary 149以降では`chrome://flags/#canvas-draw-element`を有効にして試せます。DOMコンテンツを2D canvasやWebGL/WebGPUテクスチャへ描画しつつ、インタラクションやアクセシビリティを維持することが狙いです。

HTML-in-Canvasの大きな特徴は、HTMLを単なる静止画像として貼り付けるのではなく、ブラウザがHTML要素のレイアウト、ポインターの当たり判定、アクセシビリティツリーを保持したまま、描画結果だけをcanvasやテクスチャへ渡す設計を目指している点です。

```html
<canvas id="scene" layoutsubtree>
  <div id="panel">
    <button>Buy</button>
  </div>
</canvas>
```

2D canvasでは`drawElementImage()`、WebGLでは`texElementImage2D()`、WebGPUでは`copyElementImageToTexture()`といった形でDOM要素を描画・アップロードするAPIが示されています。

これがWebXRと連携すると、HTML/CSSで作ったUIパネルを3D空間内のボード、端末画面、看板、メニュー、ゲーム内の操作端末のように扱える可能性が広がります。[Quest Browser 146.0でWebGPU in WebXRを試す](/tech-articles/quest-browser-146-webgpu-webxr)の記事でも触れたように、Quest BrowserでもHTML-in-Canvasの実験的な動作が報告されています。

ただし、WebXRとの統合仕様はまだ議論中です。2026年5月のImmersive Web対面会議（face-to-face）でもHTML-in-CanvasのWebXR対応が議題に上がり、[議事録](https://www.w3.org/2026/05/19-immersive-web-minutes.html)では入力処理、イベントの伝播方法、レイヤーとの関係、同一オリジン制約などが主な課題として挙げられています。あわせて、まずは空間上の平面パネル（quad in space）から始めるのが妥当ではないかという方向性も話し合われました。

このようにHTML-in-Canvasは有力な候補ですが、現時点で本番のWebXRアプリへ広く導入できる標準機能ではありません。実験や将来設計の材料として追っていく段階です。PlayCanvasでの具体的な実装例は、[PlayCanvasでHTML-in-Canvasを使う](/tech-articles/playcanvas-html-in-canvas)にまとめています。

## Webページ自体を空間化するSpatial CSS

もう一つの大きな流れがSpatial CSSです。

[WebKitのCSS Spatial Layout解説文書](https://github.com/WebKit/explainers/blob/main/css-spatial/explainer.md)では、相対・絶対配置、`inset`、アンカー配置、ボックス整列といった既存のCSS概念をz軸方向へ拡張し、ページ内の要素を実際の奥行きに配置する仕組みが説明されています。WebXRを置き換えるのではなく、通常のWebページの中で奥行き表現や空間レイアウトを扱うことが目的と明記されています。

Spatial CSSが実現すれば、通常のカードや見出しをCSSだけで手前に浮かび上がらせたり、ページの一部に3Dポータルを設けたり、3DモデルにDOMラベルを紐づけたりといった表現が可能になります。

```css
.product-card {
  spatial: page;
}

.product-card:hover img {
  position: relative;
  inset-back: 1cm;
}
```

アプリがXRセッションを開始して毎フレーム描画し、コントローラーやハンドトラッキングを処理するWebXRとは異なり、Spatial CSSはWebページそのものを空間対応させるアプローチです。

2026年5月の[Immersive Web WG/CGとCSSWGの合同議論](https://www.w3.org/2026/05/20-immersive-web-minutes.html)でも、Spatial LayoutはCSSを軸に空間表現をWebへ持ち込む提案として取り上げられ、3Dコンテンツと2D DOMを同じ仕組みの上でどう統合するかが議論されました。

[Safari 27 betaでvisionOS向けImmersive Webが前進](/tech-articles/safari-27-beta-visionos-immersive-website-environments-webxr)で紹介したように、Appleプラットフォームでは`<model>`要素や没入型APIが別軸で進んでいますが、Spatial CSSはWebページ全体の空間化に関わる、さらに広いレイヤーの取り組みです。

## 空間UIの質感を扱うbackground-material

Spatial CSSに近い話題として、`background-material`も提案されています。OSが備えるガラス風、パネル風、ポップアップ風といったシステム定義のマテリアルをCSSから利用できるようにする仕組みです。[WebSpatialの解説文書](https://github.com/webspatial/WebSpatialExplainers/blob/main/background-material/explainer.md)では、`background-color`を指定できる要素の背景にシステム定義マテリアルを描画するCSSプロパティとして説明されています。

WebXRの描画APIではありませんが、空間Web UIの設計では見落とせない要素です。Apple Vision ProやAndroid XRのような空間コンピューティング環境では、Webページのパネルが周囲のOS UIと自然に馴染むかどうかが体験の印象を大きく左右します。

ただし、こちらもまだ提案・議論の段階にあります。現時点ですぐ実用できるAPIとしてではなく、空間Web UIの将来像として押さえておくのが現実的です。

## 用途に応じたUI方式の選び方

今WebXRアプリを開発する場合は、用途ごとにUIの実装方法を使い分けるのが現実的です。

AR画面の上に説明や設定UIを重ねるならDOM Overlayが有力な選択肢になります。3D空間内で完全に没入型のUIを作るなら、three.jsやPlayCanvasなどの3D UI、テクスチャ、レイキャスティングを組み合わせる方法が安定しています。

HTML-in-Canvasは、HTML/CSSのUIを3D空間内のテクスチャとして扱う将来候補です。Chrome Canaryやオリジントライアルで検証する価値はあるものの、本番採用にはブラウザ対応状況とAPI変更リスクを見極める必要があります。

Spatial CSSは、WebXRアプリというよりWebページやブラウザUI自体が空間対応していく流れです。将来的に、これまでWebXRでしか作れなかった空間UIの一部をCSSで表現できるようになる可能性があり、開発者としても動向を追っておく意味があります。
